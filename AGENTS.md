# AGENTS.md — sbe-requests (Заявки на испытания)

SBE-плагин «Заявки на испытания»: локальная БД-кэш заявок + синхронизация с lab-service
(сервер — канон), файлы заявок в S3 (`sbe-doc`).

## Назначение (текущее)

- **Синхронизация** с сервером `https://epyur.fvds.ru` через JWT из ЦУП СБЕ
  (`getService('sbe-apstore').auth.getToken('lab')`): push `/api/lab/sync/push`,
  pull `/api/lab/sync/pull`. Сервер — канон, локальный JSON — кэш. Конфликты заявок — LWW
  по `updated_at`. Справочники/проекты/группы в pull — полный слепок (заменяются целиком).
- **Локальная БД**: `yourbase/sbe_requests/requests_data.json`
  (`{"requests": [...], "projects": [...], "groups": [...], "labs": [...], "methods": [...], "objects": [...]}`).
  Модель совместима с серверной (lab-service).
- **Справочники**: лаборатории/методы — **только чтение** (наполняются в ЛИМС, в заявку
  подтягиваются оттуда); объекты — создание editor+ (server); проекты (дерево parent_id,
  code уникальный) — editor; группы (создание/участники, владелец или admin).
- **Нумерация** (сервер): `{NNN}/{yyyy}` — сквозной счётчик по году, не зависит от проекта.
  Заказчику: `{projectID}-{NNN}/{yyyy}-{labID}-{methodID}`; лаборатории: `{NNN}/{yyyy}-{methodID}`
  (без labID). Номера присваиваются сервером при создании заявки/метода.
- **Файлы**: загрузка в S3 через сервис (`POST /api/lab/file`, multipart: `request_id` + `file`),
  ключ и URL хранятся в заявке (`files[]`). Загрузка через **rclone CLI** внутри сервиса.
- **Точка входа** — магазин: «Установленные → Открыть» (`publishService('sbe-requests', {open})`).
- Статусы заявки: `new` / `processing` / `completed` (смена — editor+, сервер валидирует).
- Видимость (сервер): owner ИЛИ участник группы заявки; admin — все.

## Структура

| Файл | Что это |
|---|---|
| `src/main.ts` | `SbeRequestsPlugin`: настройки, БД, syncService, view, publishService |

| `src/services/sync.service.ts` | `RequestsSyncService`: sync/push/pull, создание справочников/проектов/групп, участники, статусы, файлы, permissions/common-access, JWT, multipart, таймауты |
| `src/ui/requests-view.ts` | `RequestsView`: дерево проектов → заявки, карточка заявки, создание/правка, группы, справочники, файлы, статусы |
| `src/ui/settings-tab.ts` | Настройки: apiUrl + «Права доступа» (роли viewer/editor/admin + общий доступ) |
| `src/types/requests.ts` | `LabRequest`, `LabProject`, `LabGroup`, `Lab`, `LabMethod`, `LabObject`, `RequestMethod`, `RequestFile`, `RequestsDbData`, `PullResponse`, `PushResponse`, `UploadFileResponse` |
| `src/styles.css` | Классы `tn-req-*` на семантических токенах |

`apiUrl` (default `https://epyur.fvds.ru`). Роли lab: `viewer`(1) < `editor`(2) < `admin`(3).

- **Визуальные карточки**: список заявок (`renderView`) переведён с `<table class="tn-table">`

  обнаружено и исправлено: `.tn-req-methods`/`.tn-req-group-card`/`.tn-req-object-section`
  годами ссылались на **несуществующую** CSS-переменную `--border-divider-default`
  (её нет ни в sbe-core/design/tokens.css, ни где-либо ещё в проекте) — рамка у этих
  блоков никогда не отображалась. Заменено на реальные токены sbe-core
  (`--tn-card`/`--tn-border`/`--tn-radius`), плюс фон — теперь видимые карточки.
- **Баг-фикс (обнаружен пользователем на импортированной заявке): «ЕКН заполнен, но
  Продукт не известен», а после «Сохранить» пропадали номер партии и название.**
  Причина в двух местах:
  1. `saveManualEknProduct`/сохранение объекта (`createObject`) при каждом
     сохранении заявки создаёт НОВЫЙ объект на сервере (обновления объектов "на
     месте" не существует) — но локальный кэш `requestsDb.objects` обновляется
     только целиким `replaceReferenceData` (полный pull). Сразу после сохранения
     (включая тот же экран) поиск объекта по новому `object_id` в локальном кэше
     не находил ничего — все характеристики выглядели пустыми, хотя на сервере
     всё сохранилось верно. **Исправлено**: новый метод `RequestsDatabase.addObject`
     (upsert по id) — вызывается сразу после `createObject()`, до любого повторного
     рендера.
  2. При открытии на редактирование заявки, где `ekn` задан, но локально
     сохранённого `ekn_snapshot` нет (типично для заявок из email-импорта —
     импорт никогда не запрашивал справочник ЕКН), форма сразу показывала
     «неизвестный продукт», хотя номер валиден. **Исправлено**: в этом случае
     форма сама делает точный лукап через `lookupEknExact`, как при вводе
     нового номера — раньше приходилось руками удалять и заново вводить цифру.
  Соответствующий фикс на стороне email-импорта (lab-service) и разовый backfill
  уже импортированных заявок — см. `lab-service/AGENTS.md` (2026-08-22).
- `npx tsc --noEmit`/`npm run build` — чисто. Версия 0.1.14 → 0.1.15.

### 2026-08-21 — v0.1.14 (целевой показатель: обязательный выбор по методу вместо свободного текста)
- **По просьбе пользователя**: свободное поле «Целевой показатель» убрано из формы
  заявки. Раздел «Определяемые показатели» (был чисто информационным списком без
  действия — ничего никогда не читало состояние его чекбоксов) стал **«Целевой
  показатель»** — обязательный одиночный выбор (radio, не checkbox), **отдельная
  группа на каждый выбранный метод** (у ГГ/ГВ/РП разные шкалы значений, общий выбор
  между методами не имеет смысла).
  - Предзаполнение из ЕКН: обнаружено, что QRC хранит целевые классы прямо в
    `groups.fire_characteristics` — `flame_group` (Группа горючести → метод ГГ),
    `flammability_gr` (Группа воспламеняемости → ГВ), `flame_spread_gr` (Группа
    распространения пламени → РП), значения вида «Г4»/«В2»/«РП1» — совпадают буква
    в букву со значениями `methods.determinable_indicators`. Новая карта
    `FIRE_GROUP_FIELD_BY_METHOD_CODE` в `requests-view.ts`; `sync.service.getEknProduct`
    теперь дополнительно читает эти 3 поля из `product.data` (сырой ответ QRC,
    ранее не использовался за пределами name/thickness/sto) и кладёт в
    `ekn_snapshot.fire_groups`. Методы без известного поля (МП/КП/КИ) — только
    ручной выбор, автоподстановки нет.
  - Если ЕКН не распознан (или значение из QRC не входит в список показателей
    метода) — по умолчанию **ничего не выбрано**, сохранение заблокировано
    Notice-ом с именем метода, пока пользователь не выберет один показатель
    вручную.
  - Валидация методов/показателей перенесена в начало обработчика сохранения —
    **до** создания объекта/сохранения карточки в справочнике ЕКН (иначе при
    недостающем показателе остался бы висящий объект без заявки).
  - Хранение: `ObjectCharacteristics.target_indicator` (одна строка) заменён на
    `target_indicators: Record<methodId, значение>` — нужен per-метод, а не
    per-объект (объект общий для всех под-заявок одной заявки). Старое поле
    оставлено в типе только для чтения объектов, которые пишет `email_ingest.go`/
    `import_history.go` (другой смысл — `aim_indicator` из письма, не трогали).
  - Карточка заявки (и в sbe-requests, и в sbe-lims, см. `sbe-lims/AGENTS.md`)
    показывает выбранный показатель: «🎯 Целевой показатель: {значение}».
  - Удалена `indicatorsForMethods` (стала мёртвым кодом после переписывания
    `updateIndicators`).
- **Отдельно** (обнаружено при живой проверке ЕКН): толщина из справочника
  приходила как «100 MILLIMETER» — исправлено на стороне `ekn-service`
  (`extractThickness`/`numericPrefix`, см. `server_back/ekn-service/AGENTS.md`),
  здесь только клиент, который эти данные показывает/сохраняет — сам фикс не в
